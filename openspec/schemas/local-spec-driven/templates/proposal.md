# Proposal

## 为什么

用一到两段说明当前问题或机会、受影响对象，以及为什么现在需要处理。这里回答 why，不预设技术方案。

## 变更内容

逐条写出新增、修改或移除的可观察能力。破坏性变化必须标记 **BREAKING**，并说明受影响方。

## 能力

### 新增能力

列出本次引入的 capability。名称使用 kebab-case；每个名称都必须生成对应的 `specs/<capability>/spec.md`，并用一句话界定行为范围。没有新增能力时明确写“无”。

### 修改能力

只列出既有 capability 中发生 requirement 级行为变化的部分，并沿用 `openspec/specs/` 中的准确名称。纯实现改造不属于修改能力；没有修改时明确写“无”。

## 影响范围

列出受影响的用户、业务流程、外部 API、依赖系统、数据兼容和运维流程。技术选型及迁移步骤留给 design.md。
