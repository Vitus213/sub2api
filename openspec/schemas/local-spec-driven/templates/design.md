# Design

## 上下文

说明当前架构、约束、相关方和已存在的实现模式。引用 proposal 的动机与 specs 的 Requirement/Scenario，不在这里重新定义业务行为。

## 目标/非目标

### 目标

列出本设计必须实现的技术结果，并对应到已确认规格。

### 非目标

明确本次不解决的技术问题，防止实现范围扩张。

## 决策

逐项记录关键技术决策、选择理由、被比较的备选方案及不采用原因。数据库、缓存、锁、类、模块、表字段、事务、并发、安全、性能与可观测性等实现内容放在本节。不能只写“按 spec 实现”。

## 风险/取舍

使用“风险 → 缓解措施”的形式，说明已知限制、失败模式和剩余风险。不得用 design 放宽 specs 的可观察行为。

## 迁移与回滚

按可验证顺序说明数据或配置迁移、兼容窗口、发布步骤、回滚触发条件和回滚方法。没有迁移时说明为何不需要。

## 未决问题

只保留不阻断当前规格确认、但必须在对应 task 前解决的问题；写明负责人或解决门禁。任何会改变外部行为的问题必须先返回 specs，而不能留在本节猜测。
